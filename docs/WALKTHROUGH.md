# How Pocket Codex works

This guide is intended for someone learning Rust by reading a real, small app.
Read the modules in this order: `main`, `web`, `model`, `store`, `jobs`, `codex`,
then `auth`. Read `public/app.js` alongside the HTTP handlers when tracing a UI action.

## 1. Start with the shape of the program

```text
Browser                         Rust                              Codex CLI
   │                             │                                    │
   │ POST a message              │                                    │
   ├────────────────────────────>│ save message + queued job as JSON   │
   │ 202 Accepted + job id       │                                    │
   │<────────────────────────────┤                                    │
   │                             │ worker takes job from bounded queue │
   │                             ├── JSONL thread/start or resume ────>│
   │                             ├── JSONL turn/start ────────────────>│
   │ SSE text/progress           │<── notifications and replies ──────┤
   │<────────────────────────────┤ save text and image metadata         │
   │                             │                                    │
   │ GET an image by its id      │                                    │
   ├────────────────────────────>│ stream the image file from disk      │
   │<────────────────────────────┤                                    │
```

There are two different streams here:

- Rust talks to Codex through **stdio**: the child's standard input/output pipes.
- Rust talks to the browser through **SSE**: a long-lived HTTP response.

They are separate. The browser never sees raw Codex RPC, local file paths from
the tool, or your Codex login credentials.

## 2. `main.rs`: assemble the pieces

`Config::parse()` uses Clap to turn CLI arguments and environment variables into
a typed struct. Validation rejects binding to a non-loopback address: ngrok is
the intended remote entry point.

The startup sequence is:

1. Open the data directory and acquire its process lock.
2. Generate or load the private access key.
3. Bind the local HTTP port.
4. Start a background worker.
5. Assemble the HTTP router and serve requests.

The listener is bound before the worker starts. If port 8787 is already occupied,
we fail before launching a Codex subprocess.

`Arc<T>` means **shared ownership**, not automatic mutability. The HTTP handlers
and background worker share the same store and queue. Mutable parts use locks.
Two Tokio worker threads handle asynchronous work; there is no thread per HTTP
request. Waiting for a network connection or child output yields to other tasks.

Ctrl+C signals the worker and event streams to stop. The Codex child has
`kill_on_drop(true)`, so dropping its owner kills the private process.

## 3. `model.rs`: decide what goes in JSON

`Chat` owns its messages, image metadata, and jobs. Serde derives convert these
Rust structs to and from JSON.

An abbreviated file looks like this:

```json
{
  "version": 1,
  "id": "a-chat-uuid",
  "title": "Birthday invitation",
  "created_at": 1791414000,
  "updated_at": 1791414040,
  "codex_thread_id": "the-thread-id-returned-by-codex",
  "messages": [
    {
      "id": "a-message-uuid",
      "role": "user",
      "text": "A peach and green birthday invitation",
      "media_ids": [],
      "created_at": 1791414000,
      "job_id": "a-job-uuid"
    }
  ],
  "media": [],
  "jobs": []
}
```

The UUID labels here are illustrative; real IDs are UUID strings generated by
the server. `version` lets future releases identify the storage format.

Images are **not** encoded into this JSON. A `Media` record identifies a binary
file, MIME type, size, origin (`reference` or `generated`), and producing job.
This avoids re-serializing megabytes of image data every time a message changes.

Jobs transition through:

```text
queued → running → complete
                 → failed
queued/running   → cancelled
queued/running   → interrupted (server restart)
```

`busy()` checks for queued/running work. A chat may have only one such job,
preventing competing turns in the same Codex conversation.

## 4. `store.rs`: safely edit ordinary files

`Store::update(id, closure)` does three things under one mutex:

1. Read the current JSON file.
2. Let the closure change the in-memory `Chat`.
3. Serialize it and atomically replace the file.

Why hold the lock across all three? Suppose two requests both read an old file.
One appends a message and the other changes the title. If each writes its own
copy, the last writer can erase the first change. Serializing the complete
read/edit/write operation prevents that lost update.

Atomic replacement uses a temporary file **in the destination directory**, writes
the complete data, flushes the file to disk, then replaces the destination. If
serialization or writing fails before replacement, the previous file remains.
This does not claim full protection against every power-loss/filesystem scenario;
backups still matter.

There is also an OS-backed exclusive lock on `.server.lock`. A second server
cannot open the same directory. The JSON mutex protects tasks within one process;
the file lock protects against a second process.

The store does not keep full chat histories cached in memory. Listing projects
reads each chat and returns a small summary. This trades disk work for simplicity
and low idle memory. The small metadata reads/writes are synchronous while the
store mutex is held. For much larger deployments, move that work to a dedicated
blocking worker or change the storage design; this app targets a small private
installation.

Uploads and generated images get server-generated filenames. The browser passes
UUIDs, never filesystem paths. The serving path is canonicalized and checked
against its expected media directory before opening the file.

## 5. `web.rs`: the browser-facing contract

Axum routes map an HTTP method and path to a Rust async function. Extractors
construct the function's inputs:

- `State<App>` gets shared application state.
- `Path<String>` gets a project UUID from the route.
- `Json<Prompt>` parses and validates the request body shape.
- `Multipart` reads an image upload.

`send_message` checks text length, mode, attachment count, and project existence,
then delegates to `Queue::submit`. It returns **202 Accepted**, because the job
was accepted for later work. A completed model response does not have to fit
inside the original HTTP request's lifetime.

Middleware runs around handlers. The outer layer adds security headers. The
request-policy layer checks mutating requests' origin and custom header. The
authentication layer protects all private API routes, including images and SSE.

No cross-origin access is enabled. With an ngrok origin configured, the frontend
and API share that HTTPS origin. Without it, mutating requests are accepted only
from the loopback browser origin.

The image handler opens a registered file and streams it with `ReaderStream`,
instead of reading the entire download into RAM. That distinction matters for
concurrent image views.

## 6. `jobs.rs`: make work independent of the browser

The queue is a bounded Tokio `mpsc` channel. `mpsc` means multiple producers,
single consumer: HTTP handlers submit jobs; one worker receives them.

`try_reserve()` obtains a queue slot **before** the JSON file changes. If the
queue is full, the request fails without creating a stranded queued job. Once
the queued message and job are saved, a cancellation token is registered and
the job is sent to the worker.

The worker processes one turn at a time. That limits peak memory, keeps the
stdio protocol owner simple, and avoids concurrent generations unexpectedly
using your account's limits.

`tokio::select!` waits for whichever completes first:

- The Codex turn.
- A user pressing Stop.
- The turn timeout.
- Server shutdown.

Cancellation attempts a `turn/interrupt`, then drops the private subprocess.
Dropping on cancellation/error prevents late output from an old turn being
misattributed to a subsequent job. A future job starts a fresh process and
resumes the recorded thread. Cancellation cannot guarantee that a request
already sent to the provider incurs no usage.

The worker collects text deltas, persists partial text about once a second, and
sends browser events. It captures `imageGeneration` completion items, reads the
saved file from the permitted workspace (or decodes a bounded base64 result),
copies the binary image into app storage, and attaches its metadata to the reply.

Generate mode checks that at least one image actually returned. A textual promise
to make an image is not reported as successful generation.

## 7. `codex.rs`: a small protocol client

`Command` launches `codex app-server --listen stdio://`. The executable has piped
stdin/stdout. Rust writes one JSON object followed by a newline and reads the
same format back. This is JSONL.

Initialization is a handshake:

```json
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"pocket_codex","version":"0.1.0"},"capabilities":{"experimentalApi":true}}}
```

After the reply, the client sends an `initialized` notification. The real code
also supplies a client title.

Each outgoing request has an increasing numeric `id`. Its reply has the same
ID. Notifications have a `method` but no request ID. They can arrive **while a
request is waiting for its reply**, so `rpc_inner` buffers notifications rather
than discarding them. This is especially important for a fast `turn/start`.

The flow then uses:

- `account/read`: check whether the local CLI is authenticated.
- `modelProvider/capabilities/read`: report native image support when available.
- `thread/start`: create one model conversation for a web project.
- `thread/resume`: continue its saved conversation.
- `turn/start`: supply text and any local reference-image paths.
- `turn/interrupt`: attempt to stop active work.

Server-originated requests, such as approvals or client-executed tools, get an
explicit RPC error. This frontend cannot silently approve a shell command or
answer an arbitrary external-tool prompt.

The Codex subprocess inherits the CLI's home unless `--codex-home` overrides it.
Selected execution/control features are disabled by command-line flags. That
reduces the exposed capabilities but does not turn the process into an isolated
OS account. Read the README's isolation boundaries before sharing the app.

## 8. `auth.rs`: keep the public tunnel private

The access key contains two random UUIDs' worth of entropy and is stored locally
in `data/.access-key`. It is never embedded in frontend assets or committed.

On successful login, the server creates a separate random session token. The
browser stores it in an HttpOnly, SameSite=Strict cookie; JavaScript does not
read it. With HTTPS configured, it is also Secure. Only a SHA-256 digest of the
session token is stored in server memory. The login-key digest comparison uses
a constant-time comparison.

SHA-256 is appropriate here because the key is **random and long**. This is not
a pattern for hashing human-chosen passwords; those would require a password
hashing function such as Argon2. Do not replace the access key with a short word.

At most eight live sessions are retained; sessions expire after seven days.
Restarting the server clears the session map, so browsers must sign in again.
Wrong login attempts are limited globally to ten per minute.

## 9. `app.js`: a tiny client with server-owned history

The browser keeps transient UI state: which project is open, unfinished drafts,
selected references, and text currently streaming. Saved history comes from the
server. Chat contents and login keys are not saved to localStorage.

The `api()` helper attaches the custom mutation header, sends cookies, and
converts failures into messages. `EventSource` opens the authenticated SSE
connection. Events either update the current text bubble or schedule a fresh
server snapshot. Event reconnects always resync; the browser does not assume it
received every delta while disconnected.

Text is rendered using DOM nodes and `textContent`, not `innerHTML`. A small
formatter supports bold, inline code, and headings without trusting model text
as HTML. User-provided project names and filenames follow the same rule.

Downloads use authenticated server URLs. "Use as reference" adds an existing
image ID to the next message, so editing doesn't require a re-upload.

## Good learning exercises

Try these in increasing order of complexity:

1. Change the CSS palette and rebuild. Notice how embedded assets update only
   after compilation.
2. Add a Rename project button using the existing PATCH endpoint.
3. Add a prompt preset by adding a starter card with `data-prompt`/`data-mode`.
4. Add a storage-usage view that totals file sizes without loading image bytes.
5. Implement a deliberate project archive operation, with tests that preserve
   media and prevent archiving a running job.

For each change, trace one user action through the frontend, handler, store, and
worker. Keeping the path concrete makes Rust ownership and async code easier to
understand than learning each concept in isolation.
